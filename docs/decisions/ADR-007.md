# ADR-007 — Light theme design constraints

**Status:** Accepted

## Context

The gloam collection includes both dark themes (where tokens must be light enough to contrast against a dark background) and light themes (where tokens must be dark enough to contrast against a light background). Light themes invert several of the default design assumptions.

As of this ADR, the light themes in the collection are: Parchment, Daybook, Cirrus, Solano, Saffron, and Ochre.

## Decision

Light themes in gloam are subject to a set of additional design invariants that differ from dark theme rules. These invariants are documented here to prevent contributors from inadvertently applying dark-theme conventions to light themes.

### Invariant 1: Contrast direction is reversed

In dark themes, semantic tokens are lighter than the background and must pass contrast as light-on-dark.

In light themes, semantic tokens are **darker** than the background and must pass contrast as dark-on-light.

The same WCAG AA minimum (4.5:1) applies, but the direction of measurement is inverted: token hex values are numerically lower (darker) than the background hex values. A light theme with a bright accent token has failed this invariant.

**Test:** `wcagContrast(token, background) ≥ 4.5:1` — this is symmetric; the same formula applies to both dark and light themes.

### Invariant 2: ANSI 15 (bright white) is near-background, not bright white

In dark themes, ANSI slot 15 is the brightest foreground color — pure white or near-white. Syntax highlighters use it for "near-white" text elements.

In light themes, ANSI slot 15 must be set to a **near-background** color — a slightly lighter version of the background or an imperceptible tint. Setting it to pure `#FFFFFF` or any bright color creates a jarring bright element against a light background.

The value for ANSI 15 in all gloam light themes is a slightly lightened or neutralized version of the background hex (e.g., Cirrus uses `#F0F4F8` for background `#EEF1F6`).

### Invariant 3: All 16 ANSI colors must be darker than the background

In dark themes, ANSI palette values range from very dark (near background) to very bright. In light themes, the entire 16-color range must be **darker** than the background to remain readable.

This includes ANSI 7 ("white"/"light gray") — in dark themes this is typically a light gray, but in light themes it must be a mid-dark warm or cool gray that contrasts against the light background. ANSI 7 on a light background should achieve at least 4.5:1 contrast to be usable as "dimmer text."

### Invariant 4: Bold text requires "Use bright colors for bold" disabled in iTerm2

Most terminals offer an option to render bold text using the "bright" ANSI color variant of the current foreground. In dark themes, this is often acceptable — bright foreground on dark background is readable.

In light themes, this option must be **disabled** in iTerm2 (`Preferences › Profiles › Text › Use bright colors for bold text` → off). If enabled, bold text would use a bright color against the light background, which may produce low contrast or invisible bold text.

The `ui.bold` field in light theme JSON must be set to a **darker** value than the foreground — the deepest near-black in the theme palette. This is the opposite of dark themes where bold is typically the same as foreground.

### Invariant 5: The `dim` modifier behaves differently on light backgrounds

Starship's `dim` style modifier reduces the rendered intensity of a color. On dark backgrounds, `dim` makes a light color appear as a medium-intensity color. On light backgrounds, `dim` further reduces the intensity of an already-dark token — a `fg:muted dim` token may approach invisibility on a very light background.

When designing light themes, verify that `dim`-modified tokens (primarily `fg:muted dim` used for fill and command duration) remain visually distinguishable from the background at the actual terminal rendering. The `muted` token's WCAG contrast at full intensity should be comfortably above 4.5:1 to leave room for the dim reduction.

All gloam light themes target `muted` at ≥ 5.0:1 contrast (above the AA minimum) to ensure `dim`-reduced rendering remains marginally readable.

## Consequences

**Positive:**

- Centralising these invariants in one ADR prevents duplication across six individual theme MDs. The theme MDs reference this ADR rather than restating the rules.
- New light theme contributors have a clear checklist of differences from the dark theme workflow.
- The invariants are testable: the WCAG contrast test suite (T-TST-1) catches violations of Invariant 1 automatically. Invariants 2–5 require manual verification during design.

**Negative:**

- Light themes require additional manual verification steps that dark themes do not. The ANSI palette design for light themes is more constrained — 16 colors all constrained to the darker-than-background range versus dark themes where the full lightness range is available.
- Terminal emulator support for these invariants varies: some terminals do not offer the "bright colors for bold" toggle at all, and some do not implement `dim` consistently. Light theme design must account for these platform differences.

**Documentation:** Each light theme MD includes a "Light Theme Notes" section that references this ADR and documents any theme-specific handling of these invariants. See Cirrus, Daybook, Solano, Saffron, and Ochre MDs for examples.
